1. Executive Summary & Problem Formulation

Industrial boilers are high-energy thermal vessels that generate steam or superheated hot water for power generation, chemical processing, paper mills, textile production, and industrial manufacturing. Boilers operate under severe mechanical, thermal, and chemical stress regimes—often reaching pressures between 6 to 25+ bar and temperatures in excess of 200°C. A breakdown in operational parameters can cause catastrophic structural failure, destructive pressure explosions (BLEVE - Boiling Liquid Expanding Vapor Explosion), toxic blowouts, and tube ruptures.

Traditional industrial boiler monitoring suffers from three critical bottlenecks:

  1. Localized Gauge Isolation: Physical analog dials require human walk-around audits, preventing proactive hazard mitigation during sudden thermal or pressure transients.
  2. Lack of Regulatory Telemetry Transparency: Environmental and factory safety regulatory bodies have historically lacked continuous, tamper-evident audit streams to verify compliance with statutory safety margins.
  3. Inadequate Scale & Multi-Tenant Access: Industrial facilities lack unified platforms where factory owners can view internal operations across company plants while statutory regional inspectors maintain sovereign regional visibility without unauthorized cross-company espionage.

The Smart Boiler Monitoring and Safety Management System (codenamed Boiler Black Box) is an end-to-end cyber-physical industrial IoT system engineered to solve these challenges. It acquires physical sensor data (Temperature, Gauge Pressure, Volumetric Flow Rate, and Total Dissolved Solids) at the edge via an ESP32 microcontroller, transmits authenticated encrypted packets via TLS 1.2/1.3 to a HiveMQ Cloud broker, validates and sanitizes payloads via a high-throughput Node.js ingestion daemon, stores records in Cloud Firestore under strict Zero-Trust Role-Based Access Control (RBAC), and streams reactive telemetry to a modern web application.

Core System Capabilities & Metrics
  • Sampling & Transmission Rate: 5,000 ms periodic telemetry cadence with sub-500 ms cloud transit latency.
  • End-to-End Cryptography: X.509 Root CA TLS encryption (Amazon Root CA 1) on Port 8883 preventing MITM tampering.
  • Dynamic Safety Classification: Real-time automated state determination (Normal, Warning, Danger) based on Clausius-Clapeyron thermodynamic thresholds.
  • Multi-Tenant Data Sovereignty: Declarative database rules enforcing strict boundary separation between Regulatory Inspectors, Enterprise Owners, and Administrators.

3. Hardware Architecture & Sensing Subsystems

The hardware prototype consists of a pressurized cylindrical vessel testing rig equipped with industrial transducers, signal conditioning electronics, and an ESP32 microcontroller powered through a regulated DC power distribution rail.

Figure 3.1: Physical Testing Rig featuring cylindrical boiler vessel, piping, transducers, and ESP32 controller.

3.1 Transducer Specifications & Measurement Theory

1. Microcontroller Processing Unit: ESP32-WROOM-32D

The ESP32 is powered by a 32-bit dual-core Tensilica Xtensa LX6 microprocessor clocked at 240 MHz with 520 KB of internal SRAM and 4 MB of SPI flash. Core 0 is allocated to networking (FreeRTOS TCP/IP and Wi-Fi stack), while Core 1 handles real-time sensor sampling, ADC filtering, and JSON serialization. This symmetric multiprocessing architecture prevents network operations from interfering with time-critical sensor sampling.

2. Temperature Sensing Subsystem: DS18B20 / RTD Probe

For boiler wall and thermal fluid monitoring, the system integrates a stainless steel waterproof probe. In the baseline rig, a digital DS18B20 operates over the Dallas 1-Wire bus with 12-bit resolution (0.0625°C step size). For higher temperatures (up to 400°C), a three-wire Platinum Resistance Temperature Detector (PT100 RTD) interfaced via a MAX31865 precision amplifier is employed, governed by the Callendar-Van Dusen equation: 

R(T) = R_0 * (1 + A * T + B * T^2)
Where: R_0 = 100.0 Ohms, A = 3.9083e-3 degC^-1, B = -5.775e-7 degC^-2

3. Gauge Pressure Sensing Subsystem: Piezoresistive Transducer

Operating on piezoresistive strain gauge principles, the pressure sensor measures boiler internal steam/liquid gauge pressure from 0 to 10.0 bar (extendable to 16 bar). Excited by 5.0V DC, it outputs a linear analog voltage from 0.5V (at 0.0 bar) to 4.5V (at 10.0 bar). A resistive voltage divider attenuates the 4.5V maximum output to 3.0V to remain within the ESP32 ADC1 input limit (0 – 3.3V): 

Pressure (bar) = ((V_measured - 0.5V) / 4.0V) * 10.0 bar

4. Volumetric Water Flow Subsystem: Turbine Hall-Effect Sensor (YF-S201)

Installed in the boiler feedwater line, the YF-S201 contains a lightweight plastic turbine rotor with an embedded neodymium magnet. Fluid passage causes turbine rotation past an integrated Hall-effect IC, generating a clean 5V square-wave pulse train. Connected to ESP32 hardware interrupt pin GPIO 18, the pulse frequency directly correlates to volumetric flow rate: 

Flow Rate Q (L/min) = Pulse_Frequency (Hz) / 7.5
Total Volume V (Liters) = Total_Pulse_Count / 450.0

5. Water Quality & Total Dissolved Solids (TDS) Subsystem

Water quality is critical for boiler longevity. Dissolved calcium, magnesium, and silica precipitate under heat, forming hard insulating scale on boiler tubes. A scale layer just 1 mm thick increases fuel consumption by up to 8% and causes localized metal overheating leading to tube rupture. The TDS sensor measures electrical conductivity via alternating current excitation (preventing probe electrolysis polarization): 

V_corrected = V_raw / (1.0 + 0.02 * (T_celsius - 25.0))
TDS (ppm) = (133.42 * V_corr^3 - 255.86 * V_corr^2 + 857.39 * V_corr) * 0.5

4.2 MQTT Topic Architecture & Quality of Service (QoS)

The system utilizes a clean topic hierarchy supporting geographical aggregation and granular device filtering:

  • boiler/+/telemetry: Primary time-series sensor ingestion topic.
  • boiler/+/override: High-priority manual safety valve intervention topic.
  • boiler/{state}/{district}/{company}/{boiler_id}/data: Legacy hierarchical topic format supported by prototype endpoints.
Quality of Service 1 (At Least Once Delivery) Guarantee
The ingestion pipeline enforces MQTT QoS 1. When the ESP32 publishes a telemetry packet, the HiveMQ broker stores it and waits for the Node.js ingestion bridge to process and commit the document to Firestore before issuing the MQTT PUBACK acknowledgment. If the bridge microservice crashes during processing, the broker redelivers the unacknowledged packet upon bridge restart.

5. Node.js Ingestion Bridge Microservice

The ingestion bridge (Boiler Web 1.0/boiler-mqtt-bridge/) is an enterprise Node.js 22 LTS microservice that bridges HiveMQ Cloud and Cloud Firestore. It acts as the trusted gatekeeper, enforcing strict schema validation and security enrichment before any data enters the cloud database.

5.1 Payload Schema Validation Engine (payload.js)

To prevent corrupted or malicious telemetry from entering the database, payload.js implements pure functional validation:

  • Topic Regex Matching: Verifies topic strictly follows ^boiler/([^/]+)/(telemetry|override)$.
  • ID Consistency Check: Rejects packets where payload boiler_id does not match the topic URI parameter.
  • Universal Timestamp Normalization: Transparently parses epoch seconds, epoch milliseconds, and ISO-8601 strings into unified UTC milliseconds. Imposes a 5-minute future-drift barrier: ms > now + 300000 triggers instant rejection.
  • Strict Float Coercion: Validates temperature_c, pressure_bar, flow_lpm, and tds_ppm, rejecting strings, NaN, Infinity, or empty values.
  • Boolean Normalization: Coerces true, 1, "1", "true" into native booleans; prevents indeterminate states.
// Core Validation Logic in payload.js
function normalizeMessage(topic, data, now = Date.now()) {
  const match = /^boiler\/([^/]+)\/(telemetry|override)$/.exec(topic);
  if (!match || !data || typeof data !== 'object' || Array.isArray(data)) 
    throw new Error('Invalid message');
  const [, id, kind] = match;
  if (data.boiler_id != null && String(data.boiler_id) !== id) 
    throw new Error('Boiler ID does not match topic');
  
  const result = { boiler_id: id, timestamp: timestamp(data.timestamp, now), created_at_ms: now };
  if (data.override != null) result.override = booleanValue(data.override);
  
  if (kind === 'override') {
    if (result.override == null) throw new Error('Override value is required');
    result.source = typeof data.source === 'string' ? data.source : 'hardware';
  } else {
    for (const field of ['temperature_c', 'pressure_bar', 'flow_lpm', 'tds_ppm']) {
      const raw = data[field];
      if (raw == null) { result[field] = null; continue; }
      if (!['string', 'number'].includes(typeof raw) || !Number.isFinite(Number(raw))) 
        throw new Error(`Invalid ${field}`);
      result[field] = Number(raw);
    }
    const state = String(data.device_status ?? 'online').trim().toLowerCase();
    if (!['online', 'offline'].includes(state)) throw new Error('Invalid device status');
    result.device_status = state;
  }
  return { collection: kind === 'override' ? 'override_logs' : 'telemetry', data: result };
}

5.2 Bounded Retry & Verification Pipeline (index.js)

When a packet passes validation, the bridge validates the boiler's registration against Firestore collection boilers. If valid, it enriches the document with geographical metadata (company, district, state, address) and appends a Google Cloud serverTimestamp(). Database writes are protected by a 3-stage exponential backoff retry mechanism ($1,000\, ext{ms}, 2,000\, ext{ms}$) before failing QoS acknowledgment.

6.2 Declarative Security Rules (firestore.rules)

Cloud Firestore rules implement Zero-Trust Client Access. Browser clients are completely denied write permissions across all collections. All database writes are performed exclusively by the Node.js bridge using the Google Cloud Admin SDK. 

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    function signedIn() { return request.auth != null; }
    function profile() {
      return get(/databases/$(database)/documents/users/$(request.auth.uid)).data;
    }
    function allowed(boiler) {
      return signedIn() && (
        profile().role == 'admin' ||
        (profile().role == 'owner' && profile().company != '' && profile().company == boiler.company) ||
        (profile().role == 'inspector' && profile().district != '' && profile().district == boiler.district)
      );
    }
    function allowedReading() {
      return allowed(get(/databases/$(database)/documents/boilers/$(resource.data.boiler_id)).data);
    }

    match /users/{uid} {
      allow get: if signedIn() && request.auth.uid == uid;
    }
    match /boilers/{id} {
      allow read: if allowed(resource.data);
    }
    match /telemetry/{id} {
      allow read: if allowedReading();
    }
    match /override_logs/{id} {
      allow read: if allowedReading();
    }
    // All client writes are strictly denied
  }
}

7.3 Domain Logic & Stale Data Watchdog Algorithm (data.js)

The frontend evaluates telemetry freshness through a 120-second client-side watchdog timer. If the time delta between current time and the packet timestamp exceeds 120,000 ms, the boiler status transitions immediately from Online to Stale Data, preventing operators from acting upon frozen metrics: 

// Client Domain State Machine in data.js
export function status(telemetry, event, now = Date.now()) {
  if (!telemetry) return { text: 'No Data', color: '#94a3b8' };
  if (String(telemetry.device_status).toLowerCase() !== 'online') 
    return { text: 'Offline', color: '#ef4444' };
  
  const received = timeMillis(telemetry.created_at_ms) || 
                   timeMillis(telemetry.created_at) || 
                   eventTime(telemetry);
  
  if (!received || now - received > 120000) 
    return { text: 'Stale Data', color: '#f59e0b' };
  
  return overrideValue(telemetry, event) === true
    ? { text: 'Override Active', color: '#f59e0b' }
    : { text: 'Online', color: '#10b981' };
}
